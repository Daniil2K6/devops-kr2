# КР2, вариант 1: защита за 5–7 минут

Это памятка. Команды проверок не означают, что работа уже выполнена.

## Что сказать и показать за 2 минуты

«Клиент обращается по HTTPS к Nginx на api.devops.local. Nginx завершает TLS и передаёт запрос приложению на 127.0.0.1:8001 сервера. Приложение слушает 0.0.0.0:8001 внутри своего контейнера и обращается к Redis по имени redis в сети backend. Redis не публикует порт, требует пароль и сохраняет данные в именованном томе. Старые сайты и UFW сохранены».

1. В браузере открыть https://api.devops.local/, обновить: hits растёт. Показать сертификат с SAN DNS:api.devops.local.
2. В SSH: `cd ~/kr2; docker compose ps; docker compose top; docker compose port app 8001`.
3. Показать docker-compose.yml, отдельный /etc/nginx/sites-available/kr2, PR с веткой kr2/variant-1.
4. Показать результаты аудита, сравнения UFW и снимки 06-before-kr2, 07-kr2.

Не показывать `.env`, полный `docker inspect` и `docker compose config`: они раскрывают пароль.

## Диагностика за 3 минуты

Сначала зафиксировать симптом с хоста: `curl -v --connect-timeout 3 --max-time 5 --cacert ~/kr2.crt https://api.devops.local/`.

| Симптом | Проверка в SSH | Исправление после подтверждения |
|---|---|---|
| Не разрешается имя | На хосте проверить /etc/hosts и адрес Host-only ВМ | Исправить запись api.devops.local на хосте |
| Ошибка сертификата | `openssl x509 -in /etc/ssl/certs/kr2.crt -noout -dates -ext subjectAltName` | Использовать kr2.crt, проверить SAN и имя запроса |
| Connection refused | `systemctl is-active nginx; sudo ss -tlnp` | Если Nginx остановлен: `sudo nginx -t && sudo systemctl start nginx` |
| Таймаут | `sudo ufw status numbered; ip -br a` | Сопоставить с сохранёнными правилами; восстановить конкретное изменённое правило, не отключать UFW |
| 502 | `curl --max-time 3 http://127.0.0.1:8001/health; docker compose ps; sudo tail -n 30 /var/log/nginx/kr2.error.log` | Запустить остановленный app через `docker compose up -d app`; проверить proxy_pass и порт |
| /health = ok, главная = 500 | `docker compose logs --tail 30 app redis; docker compose ps` | Запустить Redis, проверить REDIS_HOST и согласованность паролей; после исправления `.env`: `docker compose up -d --force-recreate` |
| nginx -t сообщает permission denied | `sudo ls -l /etc/ssl/private/kr2.key` | Владелец root, права 600; проверить пути файлов |

После исправления повторить тот же запрос с хоста. На защите нельзя перезагружать ВМ и откатывать снимок. `docker compose restart` не обновляет переменные окружения: требуется пересоздание.

## Ответы на 14 вопросов

1. **Два loopback.** 127.0.0.1 внутри контейнера относится только к нему. Docker пересылает запрос на сетевой интерфейс контейнера, поэтому приложение должно слушать 0.0.0.0. Ограничение внешнего доступа задаётся публикацией 127.0.0.1:8001:8001 на сервере.
2. **Секрет в истории.** Удаление файла новым коммитом не удаляет старые коммиты. Пароль обязательно сменить. Перезапись опубликованной истории требует согласования с участниками и обновления их копий; она не отзывает уже раскрытый пароль.
3. **Слои.** RUN rm создаёт новый слой, а файл остаётся в старом. Исключаем `.env` через .dockerignore до сборки. Если секрет уже раскрыт, меняем его и пересобираем образ.
4. **CMD.** Exec-форма запускает приложение напрямую, оно получает SIGTERM. Проверка: `docker compose exec app sh -c 'tr "\0" " " </proc/1/cmdline'` или `docker compose top`.
5. **Подстановка.** `${REDIS_PASSWORD}` раскрывает Compose до запуска из окружения оболочки либо .env. `$$` оставляет знак доллара для shell внутри контейнера: healthcheck получает его переменную. Один `$` заранее подставит секрет в текст проверки; возможна рассинхронизация с env_file. Не экспортировать REDIS_PASSWORD в оболочке.
6. **Пользователь Redis.** Официальный entrypoint при команде redis-server подготавливает каталог и понижает права до redis. Обёртка sh -c обходит эту ветку. Проверить реальный процесс через `docker compose top`, а не только `exec redis id`, который показывает пользователя отдельной команды.
7. **Пароль.** Redis доступен контейнерам в backend и администратору Docker. Непубликация порта ограничивает доступ снаружи, пароль добавляет аутентификацию внутри сети.
8. **Готовность.** Обычный depends_on определяет порядок запуска; service_healthy ждёт успешного PING. Иначе первые обращения к Redis могут завершаться ошибкой. Это условие само по себе не обеспечивает восстановление при последующем отказе Redis.
9. **Данные.** down удаляет контейнеры и сеть, сохраняет именованный том. down -v удаляет том и данные, в КР запрещён. Смена тега не удаляет том, но latest может сменить основную версию и нарушить совместимость данных. Нужен Redis 7 Alpine.
10. **TLS.** Сертификат devops.local не покрывает api.devops.local без соответствующего SAN. Старый --cacert не доверяет новому самоподписанному сертификату. TLS-конфигурация выбирается по SNI; для запроса без подходящего имени действует сервер по умолчанию.
11. **client.** По интерфейсу задания это значение X-Real-IP, которое Nginx устанавливает в $remote_addr. TCP-соединение приложения приходит от прокси, не от браузера. Присланные клиентом заголовки можно подделать; доверять следует заголовкам своего настроенного прокси.
12. **Перезагрузка.** Включённые systemd-службы SSH, Nginx и Docker стартуют автоматически. Контейнеры с unless-stopped поднимутся, кроме остановленных вручную. Проверить `systemctl is-enabled nginx docker` и restart в Compose.
13. **hosts.** Браузеру нужно разрешить доменное имя в адрес ВМ. Nginx использует server_name для выбора блока, а proxy_pass обращается к 127.0.0.1; разрешать api.devops.local на сервере для этого не требуется. Серверным curl по имени всё же нужно разрешение или --resolve.
14. **Docker и UFW.** Docker создаёт правила NAT и пересылки, поэтому обычные входящие правила UFW не гарантируют закрытие опубликованного порта. Старый аудит проверяет порты 5000/5432 и может пропустить 8001. Нужна проверка `docker compose --project-directory ~/kr2 port app 8001` на точное значение `127.0.0.1:8001`, а также отсутствие публикации Redis.
